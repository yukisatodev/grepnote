# 要件定義

背景・課題は [00-concept.md](./00-concept.md) を参照。ここでは「何を作るか」を機能・非機能の両面で定義する。

## 用語定義

| 用語 | 定義 |
|---|---|
| メモ | ユーザーが登録する技術メモ1件(タイトル・本文・タグ・作成日時を持つ) |
| トークン | 検索のために本文を分割した最小単位(文字bi-gram) |
| 転置インデックス | 「トークン → そのトークンを含むメモIDの集合」を保持するデータ構造 |
| スコア | あるメモが検索クエリにどれだけ関連するかを表す数値(TF-IDFベース) |

## 機能要件

| ID | 要件 | 優先度 |
|---|---|---|
| F-01 | メモを登録できる(タイトル・本文・タグ) | Must |
| F-02 | 登録済みのメモが一覧表示される | Must |
| F-03 | キーワードでメモを検索できる | Must |
| F-04 | 検索結果は関連度が高い順に並ぶ | Must |
| F-05 | 検索結果に、クエリと一致した箇所がハイライト表示される | Should |
| F-06 | タグでメモを絞り込める | Should |
| F-07 | 登録したメモはブラウザをリロードしても保持される | Must |
| F-08 | メモを削除できる | Should |
| F-09 | メモを編集できる | Could |
| F-10 | 保存・削除の操作結果を画面上でフィードバックする | Should |
| F-11 | キーボード操作だけで検索を開始・クリアできる(自動フォーカス、`/`、`Esc`) | Should |

Must=MVPに必須、Should=時間があれば入れる、Could=余力があれば。

F-10・F-11はMVP実装後、実際にブラウザで触ってみて「マウス操作前提になっていて検索ツールとして使いにくい」
「保存・削除しても反映されたという手応えがない」と気づいて追加した要件。最初の要件定義で見落としていた
ユーザビリティの観点で、機能一覧を書くだけでは気づけなかった部分。

## 非機能要件

| ID | 要件 |
|---|---|
| N-01 | サーバーを持たず、静的ホスティング(GitHub Pages)のみで動作すること |
| N-02 | 外部API・外部ライブラリの辞書データに依存せず、オフラインでも検索が機能すること |
| N-03 | メモが日本語・英語混在で書かれていても検索対象にできること |
| N-04 | メモ数が数百件規模になっても、検索操作で体感できる遅延が出ないこと |
| N-05 | データはユーザーのブラウザ内に閉じる(送信・共有機能は持たない = プライバシー面の要件でもある) |

## スコープ外(今回やらないこと)

意図的にやらないことを明記する。これも設計判断のひとつ。

- 複数端末・複数ブラウザ間でのデータ同期
- ユーザー認証・マルチユーザー対応
- サーバーサイドでの永続化(DB接続)
- リアルタイム共同編集
- 曖昧検索(タイポ許容・類義語展開)。bi-gramによる部分一致止まりとする

## MVPの定義

F-01〜F-04, F-07(Must要件)が動作する状態を最初のリリース基準とする。
Should/Could要件は、MVP完成後に余力を見て着手する。
