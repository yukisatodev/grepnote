# 技術選定ログ (Decision Log)

課題→検討した選択肢→却下理由→採用理由の順で記録する。
「何を使ったか」ではなく「なぜそれを選び、何を捨てたか」を残すためのドキュメント。

---

## ADR-001: UI実装にフレームワークを使わない

**課題**: メモ一覧・検索ボックス・結果表示という、状態の少ないシンプルなUIをどう実装するか。

**検討した選択肢**
| 選択肢 | 却下/採用 | 理由 |
|---|---|---|
| React + TypeScript | 却下 | 状態(メモ配列・検索クエリ・結果)が単純で、宣言的UIの恩恵よりセットアップと仮想DOMの抽象化コストが上回ると判断 |
| Vue | 却下 | 同上。加えてこの作品で見せたいのはフレームワーク習熟ではなくデータ構造・アルゴリズムの設計力 |
| Vanilla TypeScript + Vite | **採用** | DOM操作を直接書くことで、UIコードの分量を最小限に抑え、`services/`層(検索ロジック)にレビューの焦点が当たるようにした |

**結果として得たトレードオフ**: DOM更新のたびに再描画ロジックを手書きする必要があり、UIが複雑化した場合はスケールしない。今回の規模(1画面・数十件のメモ)では許容範囲と判断。

## ADR-002: 日英混在テキストのトークナイズ方式

**課題**: 検索対象のメモは日本語・英語が混在する。単語単位の分割は英語には有効だが、日本語には分かち書きの区切りがなく機能しない。

**検討した選択肢**
| 選択肢 | 却下/採用 | 理由 |
|---|---|---|
| 形態素解析ライブラリ(kuromoji等)導入 | 却下 | 精度は高いが、辞書データを含めるとバンドルサイズが大きく増え、GitHub Pagesでの配信コストと今回のスコープに見合わないと判断 |
| 空白区切りの単語分割のみ | 却下 | 日本語がほぼ分割されず、検索精度が実用に耐えない |
| 文字N-gram(bi-gram)によるトークナイズ | **採用** | 言語を判別せず、2文字ずつのスライドで機械的に分割する方式。実装が数十行で済み、日英どちらにも同じロジックで対応できる |

**結果として得たトレードオフ**: bi-gramは「意味のある単語」ではなく「文字の並び」で一致を見るため、意図しない部分一致(ノイズ)が発生しうる。検索対象が数十〜数百件規模である前提で許容し、[04-tradeoffs.md](./04-tradeoffs.md)に限界として明記する。

## ADR-003: データ永続化の方式

**課題**: 登録したメモをブラウザリロード後も保持する必要がある。GitHub Pagesはサーバーサイドの実行環境を持たない。

**検討した選択肢**
| 選択肢 | 却下/採用 | 理由 |
|---|---|---|
| 外部BaaS(Supabase / Firebase) | 却下 | APIキー管理やセットアップが増え、「小さく作り切る」というこの作品の方針から外れる。フルスタックの実演としては魅力的だが、今回は設計判断の提示を優先 |
| IndexedDB | 保留 | 大量データ・トランザクション処理に向くが、今回の想定データ量(数十〜数百件)ではオーバースペック |
| localStorage | **採用** | 同期API・実装がシンプル。`data/`層に永続化ロジックを閉じ込めているため、将来IndexedDBへ差し替える場合も他層への影響は小さい設計にしている |

## ADR-004: 検索結果のスコアリング方式

**課題**: 複数のメモがヒットした際、どの順番で表示するか。

**検討した選択肢**
| 選択肢 | 却下/採用 | 理由 |
|---|---|---|
| ヒットしたら登録順に表示 | 却下 | 関連度を反映できず、検索エンジンとして機能が弱い |
| 出現回数の単純カウント | 却下 | 長いメモほど有利になり、短くても的確なメモが埋もれる |
| TF-IDFに基づくスコアリング | **採用** | 「そのメモの中での出現頻度(TF)」と「全体でどれだけ珍しい語か(IDF)」を掛け合わせ、ありふれた語よりも特徴的な語の一致を重視する設計にした |

## ADR-005: タグの正規化をしない

**課題**: メモは複数のタグを持つ。データ構造として、`Tag`を独立したエンティティに分けて`Memo`と多対多で関連付けるか、`Memo`に`tags: string[]`として埋め込むか。

**検討した選択肢**
| 選択肢 | 却下/採用 | 理由 |
|---|---|---|
| `Tag`エンティティを分離し、`Memo`と多対多で関連付ける(中間テーブル) | 却下 | リレーショナルDBなら定石だが、localStorageにJSONで保存する構成ではJOIN相当の処理を自前で書く手間が増えるだけでメリットが薄い |
| `tags: string[]`として`Memo`に直接埋め込む(非正規化) | **採用** | 保存・読み込みがJSON構造そのままで完結し、シンプルさを優先する方針と合う |

**補足**: この判断により、扱うエンティティは実質`Memo`1つのみになった。エンティティ間のリレーションを可視化するER図は、単一エンティティでは情報量がほぼゼロになるため今回は作成していない([02-design.md](./02-design.md)のデータモデル欄を参照)。

## ADR-006: テストの範囲

**課題**: 全機能をテストするか、範囲を絞るか。小さいポートフォリオ作品での工数とのバランスが必要。

**検討した選択肢**
| 選択肢 | 却下/採用 | 理由 |
|---|---|---|
| E2Eテスト(Playwright等)まで含める | 却下 | 1画面のみのアプリでUIの複雑度が低く、導入・維持コストに見合わない |
| テストを書かない | 却下 | `services/`層(トークナイズ・インデックス構築・スコアリング)は入出力が明確な純粋関数で、最もバグを埋め込みやすく、かつ最もテストしやすい部分。ここを検証しない理由がない |
| `services/`層に絞ってVitestで単体テストを書く | **採用** | ロジックの正しさを保証したい部分と、テストが書きやすい部分が一致している。DOM操作(`ui/`層)はテスト対象から外し、目視確認で担保する |

**テスト対象**: `tokenizer`(正規化・分割・bi-gram化)、`indexer`(インデックス構築・更新)、`search`(TF-IDFスコアリング・ランキング)、`highlight`(ハイライト区間の計算)。加えて`ui/renderHighlight`のようにDOM操作を含まない純粋な文字列生成もテスト対象に含めた。特にHTMLエスケープはXSS対策として振る舞いを保証したいロジックであり、「DOM操作かどうか」より「入出力が明確な純粋関数かどうか」を境界にした方が実態に合うと判断したため

## ADR-007: トークン一致率による検索結果の足切り

**課題**: 実装後にブラウザで動作確認したところ、`"rebase"`で検索すると、`"async"`や`"Promise"`を含むメモまでヒットすることが分かった。原因は`"rebase"`のbi-gram(`re`,`eb`,`ba`,`as`,`se`)のうち`"as"`が`async`に、`"se"`がPromiseに、それぞれ意味とは無関係に部分一致するため。TF-IDFのスコアリングだけでは、こうしたノイズは下位に沈むだけで結果から消えない。

**検討した選択肢**
| 選択肢 | 却下/採用 | 理由 |
|---|---|---|
| 何もしない(スコア順の並びだけで対応) | 却下 | 上位数件はともかく、結果件数自体にノイズが混ざり続け、「関連するメモが何件あるか」の実用性が下がる |
| 形態素解析ベースの厳密な単語一致に切り替える | 却下 | [ADR-002](#adr-002-日英混在テキストのトークナイズ方式)で却下した理由(依存の重さ)がそのまま当てはまる |
| クエリのユニークトークンに対する一致率が閾値(50%)未満のメモを除外する | **採用** | bi-gram方式を維持したまま、"たまたま2文字だけ一致した"ノイズと"実質的に同じ語を含む"ヒットを区別できる。実装コストも小さい |

**閾値50%の根拠**: 厳密な理論値ではなく、実際に確認した`"rebase"`(5トークン)のノイズ例(一致率20%)は除外し、部分的な語形変化(送り仮名違いなど)による一致(一致率60〜80%程度を想定)は残す、という手触りで決めた値。データが増えた際に再調整が必要になる可能性がある(実測に基づく再チューニングの余地として[04-tradeoffs.md](./04-tradeoffs.md)に記載)。

## ADR-008: タグ絞り込みとキーワード検索の組み合わせ方

**課題**: F-06(タグ絞り込み)を実装するにあたり、キーワード検索と併用できるようにするか、複数タグを選べるようにするか決める必要があった。

**検討した選択肢(併用の可否)**
| 選択肢 | 却下/採用 | 理由 |
|---|---|---|
| タグ選択と検索キーワードは排他的(片方を使うと他方は解除) | 却下 | 「gitタグの中からrebaseを探す」のような、実際に使いそうな絞り込み方ができなくなる |
| タグとキーワードを併用可能にする(キーワード検索→結果をタグでさらに絞る) | **採用** | 実装コストが小さく(検索結果の配列をfilterするだけ)、絞り込みという言葉の直感にも合う |

**検討した選択肢(複数タグの選択)**
| 選択肢 | 却下/採用 | 理由 |
|---|---|---|
| 複数タグをAND/ORで選択できる | 却下 | 想定データ量(数十〜数百件)ではタグ自体の種類も少なく、複数選択のUIとロジックを足す複雑さに見合う価値が薄い |
| 1つのタグだけをトグルで選択 | **採用** | 実装・UIともに最小限で、今回のスコープでは絞り込みとして十分機能する |

## アーキテクチャ全体の設計判断

サーバーを持たない構成だが、あえて `api/` → `services/` → `data/` とレイヤーを分離している。
理由は、本来この種の検索処理はサーバーサイドに置かれることが多く、
「将来的にNode.js API + DBへ切り出すとしたら、どこで責務を切るか」を先に考えて実装した方が、
設計判断そのものが伝わると考えたため。

- `api/`: 疑似APIクライアント層。呼び出し方をサーバー通信を想定した形に揃えている
- `services/`: トークナイズ・インデックス構築・スコアリングなどのビジネスロジック
- `data/`: 永続化(localStorage)とサンプルデータ
- `ui/`: DOM描画とイベントハンドリングのみ。ロジックを持たせない
